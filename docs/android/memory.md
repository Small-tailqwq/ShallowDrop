# 跨对话记忆（实验性）

Android 版可以把用户在各个对话里说过的长期信息整理成记忆，注入之后的新对话。默认关闭。方案来源与选型实测见 [cross-window-memory-2026-11-17.md](cross-window-memory-2026-11-17.md)。

## 使用

「设置 → 通用 → 记忆」进入记忆页。

- **开关**：标题旁标注「实验性」。打开时弹出确认，列出三点：这是实验性功能、API 开支会增加、可能影响回答效果。关闭后不再读取和整理，已有记忆保留，仍可查看、修改和提问。
- **摘要**：注入对话的记忆条目，一条一件事，最近更新的在前。点开可修改、删除，并看到这条记忆依据的用户原话；右上角可手动添加。
- **原始**：每次记忆变动的来源记录，新的在前。来自对话的记录显示对话标题、日期、作为依据的用户原话和具体改动（新增、修改前后、删除）；手动修改和提问引起的改动也记在这里。点原话跳回原对话并定位到那条消息，原对话已删除时提示。
- **问问记忆**：底部输入框。回答同时依据摘要和原话，可以问「你怎么知道我住在杭州」，也可以直接要求增删改，改动列在回答下方并立即生效。问答不保存，离开页面即清空。
- **清空记忆**：删除全部记忆和来源记录，对话不受影响；清空后旧对话不会被重新整理。

## 三类信息

发给模型的内容分三层，记忆提示词只说明它们各自的性质，不为具体场景写规则：

| 层 | 内容 | 位置 |
|---|---|---|
| 记忆 | 过去对话里保存的背景，带记录日期，可能已经变化 | system 里的【用户记忆】 |
| 当前情况 | 发消息那一刻的时间、时区和位置，由设备给出 | 每条用户消息开头的一行括号 |
| 对话 | 历史消息与本次提问 | messages |

「现在」「今天」「这里」「附近」看当前情况，「这个人是谁、喜欢什么、家在哪」看记忆；记忆里的住处与当前位置不同说明用户此刻不在家，记忆里安排的日期早于当前日期说明已经过去；本次对话里说的话优先于两者。

### 当前情况

- 形如 `（当前情况：2026-11-17 星期二 14:30，UTC+09:00 Asia/Tokyo；位置：日本 东京）`，英文界面下为 `(Current situation: …)`。生成见 `domain/chat/CurrentState.kt`。
- 与记忆开关无关，由「设置 → 当前情况」控制：位置来源决定有没有位置，「时间与时区」开关（默认开）决定有没有时刻和时区。关掉后只剩日期和位置；两者都没有时不发送这一行。
- 官方的 `latest_reminder` 照常发送。它的五项格式由服务端校验，带不了时刻和时区，所以另加这一行。这是 Android 版相对 Web 版的扩展。
- 每轮的内容保存在回复的 `currentState` 上，之后的请求原样回放，续写沿用，不影响上下文摘要的指纹。

### 记忆的读取

记忆开启且不为空时，对话请求的 system 在助手身份说明（和语音模式说明）之后追加【用户记忆】列表和上面的说明，另有几条使用规则：只在相关时使用，一次只用直接相关的一两条；没有的信息不猜；不照抄记忆和当前情况的原文。记忆块不用 XML 标签包裹，实测带标签时 flash 偶尔把整段原样输出。摘要请求和上下文压缩不带记忆。场景实测见 [memory-scenarios-2026-11-17.md](memory-scenarios-2026-11-17.md)。

## 写入

写入参考 OpenAI Codex 的记忆管线：不在对话中调用工具，而是对话告一段落后单独请求模型提取。

- 回复完成或被停止后，会话标为待整理。以下时机整理：该会话闲置 3 分钟；在别的会话发消息前（最多等 10 秒，超时后在后台继续）；应用启动时补做上次没整理的。
- 每次只送上次整理之后的新消息（最多最近 40 条），用户消息带编号和当时的「当前情况」（用来换算「明天」「这周」、理解「这边」），助手回复截到 600 字。
- 模型只输出增、改、删操作和依据的用户消息编号，由客户端应用。让模型整体重写列表在实测中会清空记忆库，所以不用。无效操作被忽略：编号不存在、文本为空、超过 300 字、含密钥。一次删除超过一半记忆（且多于 3 条）时丢弃全部删除操作。
- 每条记忆保留最近 4 句依据的原话（文字快照，原对话删除后仍可查看）。来源记录最多保留 500 条。
- 请求失败保留待整理标记，下次再试；输出无法解析时放弃这一段。
- 删除会话、全部删除或导入历史会清掉对应的整理进度，记忆本身保留。

提取和提问固定使用 `deepseek-flash`，关闭思考和工具，输出上限 4096 token，都是单独的 API 请求。

## 篇幅

记忆随每次提问发送，所以按总字数设限，不按条数。

- **上限**：全部记忆合计 3000 字（`MEMORY_BUDGET`），单条 300 字。到上限后，新增和加长的写入被丢弃，修改和删除照常；手动添加时提示「记忆已满」。记忆页「摘要」栏顶部显示当前占用。
- **到期清理**：整理对话时，模型给有明确结束日期的短期安排（行程、预约、截止日期）标上到期日 `until`，长期事实和每年重复的日子不标。到期后 14 天内仍然注入（模型按日期知道它已经过去，能回答「上周的预约」这类问题），之后由客户端删除，不需要请求模型。记忆页的条目上显示到期日。
- **合并**：每次整理完对话后，总字数超过上限的 80% 时请模型合并一次，只允许两种操作：把同一件事或同一主题的几条并成一条、把啰嗦的一条缩写。模型不能删除；客户端丢弃以下操作：新文字没有变短、丢了原文里的数字或西文词、同一条记忆被多个操作涉及、条目在请求期间被改动。合并后的条目保留原来的记录日期和原话。合并没能压到阈值以下时，要再增长 300 字才重试。
- 清理和合并的改动都记入「原始」栏，来源显示为「自动整理」。

实测（`MemoryReliabilityTest` 的合并一段，5 遍，运行 `memory-1794918083451`）：在跑完 12 个窗口的记忆上追加 69 条零碎、重复或啰嗦的条目，共约 100 条、2010 字，合并一次。

| 项目 | 结果 |
|---|---|
| 条数 | 约 100 条减到 36 至 51 条 |
| 总字数 | 约 2010 字减到 1445 至 1550 字，少 23% 至 29% |
| 89 项具体信息（名称、型号、数字、日期） | 5 遍全部保留 |
| 被客户端丢弃的操作 | 4 遍各 1 个，1 遍 17 个；看过的一例是把「Google 的 Pixel 9」并成「Pixel 9」，因丢了一个西文词被拒 |
| 合并前后的 26 项问答 | 都是 130/130 |
| 合并前后的 7 项行为 | 各 34/35，两处不通过读过原文都是评分正则误判 |
| 出差行程的到期日 | 5 遍都标为 2026-04-17，并在 5 月 3 日的窗口被清理 |

一次合并约 2500 输入 token、1400 输出 token，耗时约 5 秒。同一版代码重跑 `MemoryScenarioTest`（运行 `scenario-1794918260119`）与改动前持平，只有「一周后问今天的安排」一项有 1/5 把上周的预约说成「昨天」（日期写对了），改动前一轮是 0/5；这条回答走的读取提示词没有改动。证据在 `android/app/build/reports/memory/2026-11-17-budget/`。

没有用向量检索按相关性取记忆：条目是几十条关于用户本人的事实，像过敏这类信息在提问里不会出现却必须常驻，而检索要多一次请求或一套嵌入模型。

## 存储

记忆存在应用私有目录 `files/memory/memory.json`，包含记忆条目、来源记录、各会话的整理进度和待整理标记。不随历史对话导出，卸载应用即删除。

## 未实现

- 图片和文件附件的内容不参与整理，只看文字。
- 没有「近期对话摘要」层，也不检索旧对话原文。
- 记忆页的问答不支持流式显示。
