# 连续五轮压缩与召回测试（2026-11-16）

MuMu Android 15（API 35），模型 `deepseek-flash`，后台阈值 45%、等待阈值 65%。全程通过 ADB instrumentation 调用真实生产 `ChatEngine` 和模型接口。五轮完整运行耗时 119.51 秒，测试后保留 45 / 65 设置。测试会话为 `compaction-multi-1794834338767`，标题「连续压缩可靠性 · 5 轮」。

结果为第二轮丢失两条旧事实，后三轮保持该损失，未继续下降，也未自动恢复。

## 样本与对照

[设备测试源码](../../android/app/src/androidTest/java/io/github/smalltailqwq/shallowdrop/domain/chat/CompactionReliabilityTest.kt) 中的 `repeatedCorpusRecall` 使用与[单轮测试](compaction-fixed-sample-2026-11-16.md)相同的首批固定样本：随机种子 `20261116`，30 章旅行档案，账册 A01–A30，各有一个随机封印代码；第 28 章更正 A01、A11、A21。A31–A35 始终未提供，正确回答为 `UNKNOWN`。

第二至第五轮各追加 28 章背景文字、10 条新代码（依次 B01–B10、C01–C10、D01–D10、E01–E10），并各更正一次 A01、A11、A21。追加样本的随机种子为 `20261116 + 压缩轮次`。新增代码分布在追加材料的第 1–26 章，最后两章只含背景。

从最初 30 条事实中排除三条持续更正的事实，固定跟踪其余 **27 条未再重复提供的旧事实**。这组事实的分母始终不变，用于观察跨轮损失。另按每轮全部已知代码、更正和未知问题分别评分，代码必须精确匹配。

每轮执行顺序：

1. 同一会话追加材料后，使用当前有效上下文回答全部测试问题，作为本轮压缩前对照。
2. 通过生产 `ChatEngine.send` 发送简短确认要求，等待真实摘要生成、采用及确认回答完成。
3. 使用新摘要及生产策略保留的近期原文，再回答同组问题。
4. 保存结果，然后继续在该会话追加下一批材料。

所有评测问题、压缩前回答和压缩后回答都在会话外请求，不写回聊天记录。会话里只增加档案与简短确认。第二轮起的压缩前对照也依赖上一轮摘要，因而用于衡量本轮新增损失；固定标准答案始终来自样本生成器，用于衡量累计损失。

各轮客户端估算上下文为 692,751–696,123 token，均自然超过 65% 等待阈值，没有伪造 usage。服务端实测压缩前输入为 582,013–598,613 token，低于客户端估算；触发依据是客户端估算。每轮都走达到等待阈值后的压缩采用流程。

- 固定旧事实累计下降 **7.4 个百分点**。第三轮之后总召回率上升，是新增的正确事实扩大了分母，遗漏的旧事实没有恢复。

## 遗漏定位

丢失的是 A29=`7ZQF6LUG` 和 A30=`T2QLTBQ5`。首轮按生产策略只总结前 28 章，A29、A30 保留原文，因此首轮摘要没有这两项属于预期行为。

第二轮压缩前对照仍能正确回答这两项；第二轮生成的新摘要没有记录它们，压缩后均回答 `UNKNOWN`。第三至第五轮的摘要和回答也持续遗漏这两项。原始消息完整性校验通过，原文仍保留在会话中。

直接证据表明损失出现在第二轮压缩前后，且已经反映在摘要文本中。本次没有修改压缩提示词或生产逻辑。
